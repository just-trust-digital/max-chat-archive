## Обоснование исправлений и ограничения

Подтверждённый дефект: разрешённый исходный URL мог ответить перенаправлением на другой хост, а `fetch` следовал ему до повторной проверки. Синтетический 302 доказал выход за список медиа; после исправления адрес назначения не запрашивается. Для такого сценария нужно, чтобы допустимый файловый сервер вернул redirect; отправка обычной ссылки на посторонний домен уже блокировалась. Это не доказательство кражи сообщений или произвольного выполнения кода.

Ограничение `storage.local`, удаление `tabs` и запрет инкогнито — усиление защиты. До исправления content script мог читать storage, что соответствует стандартной политике Chromium; не найден путь, по которому обычный скрипт сайта уже читал эти данные через имеющийся мост. Nonce в MAIN world не рассматривается как секрет от самой страницы MAX. Мост не предоставляет странице произвольный сетевой proxy или прямой доступ к IndexedDB расширения.

При первом синтетическом исследовании Playwright не перехватил второй запрос цепочки redirect. Один GET ушёл на `https://pult.justtrust.digital/bugs/report/audit-only?utm_source=jtd_dev`, получен 404; реальных данных и тела отчёта не было, использовался чистый профиль. Исключение записано, окончательный тест перенаправляет на закрытый локальный порт и блокирует переход до запроса. Остальные начальные внешние запросы в окончательной проверке либо подменены, либо отменены.

Сервер приёма, закрытый inbox, серверное хранение/удаление и GitHub-права владельца в этой работе не перепроверялись и не менялись. Срок удаления принятого обращения на сервере не установлен этим аудитом и честно отмечен в PRIVACY.md. Runtime npm-зависимостей и удалённо исполняемых скриптов у расширения нет.

Первый OSV-запрос из песочницы завершился URLError. Повтор с разрешённой сетью отправлял только названия и версии пакетов: для pypdf 6.10.0 получены 72 записи OSV, включая GHSA/PYSEC alias-записи; это не 72 независимые доказанные уязвимости продукта. Например, [GHSA-23w6-3w8w-8484](https://github.com/py-pdf/pypdf/security/advisories/GHSA-23w6-3w8w-8484) описывает чрезмерное потребление ресурсов при чтении специально подготовленного PDF. Упаковщик читает только собственную свежесозданную инструкцию, outlines не извлекает; пользовательские PDF эта библиотека здесь не обрабатывает. Зависимость всё равно обновлена до [6.21.2](https://pypi.org/project/pypdf/6.21.2/). В отдельном Python-окружении закреплены также ReportLab 4.4.9, Pillow 13.0.0, charset-normalizer 3.5.2; для всех четырёх OSV вернул 0 записей. `pip check` и полная сборка PDF/ZIP прошли. Результат — `output/security-audit/osv-final.json`; это проверка известных advisories на дату запроса, не гарантия безопасности зависимости.

Изменённый путь загрузки нужно проверить на реальных вложениях MAX перед новым выпуском: допустимые серверы с redirect теперь дадут пропуск, а не загрузку. Прежнее подтверждение владельца не покрывает новое ограничение. Обновление/откат между опубликованными версиями, повторная визуальная QA и физические устройства в этой технической проверке не выполнялись; внешность интерфейса не менялась.

## Предположения исходной сверки, проверенные выше

- `manifest.json`: `tabs`, `storage`, `downloads`; wildcard MAX/CDN; API GitHub, raw GitHub и приёмник обращений. Это поверхность для ревью, не доказанная уязвимость. Перечисленные пути host permissions не следует считать серверным разграничением доступа.
- `download-bridge.js` работает в MAIN world и обменивается `postMessage` со страницей; `content.js` проверяет source/origin/marker/nonce. Скрипты того же окна могут наблюдать обмен; нужно проверить фактические возможности злоупотребления и URL/redirect-путь, прежде чем формулировать finding.
- Поиск `incognito|inIncognito|setAccessLevel` в JS вне `test/` и `fixtures/` совпадений не дал; в манифесте явного запрета incognito нет. Реальное поведение при ручном разрешении работы в приватном окне не проверено. Это пробел проверки, не подтверждённая утечка.
- `checkpoint.js` использует IndexedDB `max-archive-checkpoints`; `reporting.js` — `chrome.storage.local`. Проверить жизненный цикл копий и доступ из разных контекстов. Отдельного privacy/security документа поиск по именам файлов не обнаружил; README уже описывает отправку обращений и ограничения обезличивания, поэтому описание данных следует дополнить, а не создавать противоречащий ему текст.
- `docs/development.md` прямо отмечает отсутствие отдельного прогона реального MAX для 0.3.20 и более ранних проверенных макетов. Исторические визуальные/серверные результаты в документации не являются новой проверкой в этой сверке.

На этапе исходной сверки сканеры и браузерная установка ещё не выполнялись, поведение не менялось. Эта историческая граница заменена результатами расширенного аудита выше; не использовать исходную таблицу как текущий статус.
