# Статический разбор двух расширений экспорта MAX

Проверено 20 октября 2026 года. Пакеты скачаны из официальных каталогов, распакованы только в `.research/`. Расширения **не устанавливались, их код не запускался**. Это разбор реализации, а не проверка полноты на реальном аккаунте. Комментарии авторов о проверке MAX приведены только как контекст; независимо здесь не подтверждены.

## Главное для проблемы «только 30 сообщений»

### 1. Firefox выбирает контейнер истории явно

В `.research/firefox/content.js:8-10` заданы `div.history`, `div.item`, `div.bubble`. Функция `getScrollable` сначала ищет **`div.history .scrollable`**; только при отсутствии такого элемента перебирает потомков истории с переполнением (`content.js:959-970`). `scrollChat` при каждом вызове заново получает контейнер, ставит `scrollTop` в 0 или `scrollHeight` и отправляет `scroll` (`973-977`).

**Практическая проверка:** сопоставить в живом MAX ближайший overflow-предок `.messageWrapper` с `.history .scrollable`: узел, классы, связь с первым сообщением и геометрия. Если это разные элементы, движение нашего `scrollTop` ещё не доказывает, что скроллится элемент, запускающий подгрузку. Совпадение необходимо проверять, а не заменять селектор вслепую.

### 2. Firefox начинает экспорт после перезагрузки, затем ждёт стабилизации

Обработчик START сохраняет параметры в `sessionStorage` и вызывает `location.reload()` (`content.js:1473-1484`). После перезагрузки ожидает появления истории и хотя бы одного item до 60 секунд, затем три последовательные секунды неизменного количества item (`715-736`). Перед чтением старой истории догружает новые сообщения: нажимает кнопку, найденную через `span.scrollButtonCounter`, повторно скроллит вниз с интервалом 350 мс и требует одновременно стабильности DOM и отсутствия кнопки (`980-1021`, вызов `1245-1250`).

**Практический вывод:** свежий выбранный чат и уже открытый чат могут иметь разную готовность загрузчиков; это согласуется с нашим наблюдением, но не устанавливает причину. Нужен отдельный тест запуска из закрытого чата, ожидание готовности фактического scrollpane и проверка свежего/старого края. Перезагрузка у конкурента — интересная стратегия восстановления, а не доказательство необходимой перезагрузки в нашей реализации.

### 3. Критерии остановки не доказывают полноту

Firefox каждый проход ставит историю в верхнее положение, ждёт 350 мс и сравнивает число `div.item`. Остановка — 12 стабильных проходов без дат или 20 с датами (`1233-1236`, `1261-1292`). Есть отдельный выход по достигнутой начальной дате (`1268-1273`) и проход после цикла (`1295-1301`).

Chrome получает ближайшего overflow-предка первого wrapper (`.research/chrome/content.js:40-52`), сохраняет его на весь цикл, ставит `scrollTop=0`, ждёт 450 мс. Стабильность — первые 120 символов первого сообщения плюс количество wrapper; выход после трёх совпадений, максимум 80 проходов (`204-228`). Сообщения извлекаются из DOM после автопрокрутки (`231-245`).

**Вывод:** Chrome использует близкий к нашему принцип выбора scrollpane; его пакет сам по себе не даёт решения бага. Ни один из рассмотренных циклов не получает от сервера явный признак конца истории. Отсутствие роста DOM нельзя объявлять доказательством полного архива.

## Даты, идентификаторы и большой объём

- Firefox обходит капсулы дат и bubble **в общем порядке DOM**: `span.capsule, div.bubble`; обновляет контекст на капсуле и прибавляет время сообщения (`content.js:307-347`). Это полезно, когда один item содержит несколько дат/сообщений. Дата хранится вместе с записью сразу при обнаружении сообщения, не вычисляется только по итоговому DOM.
- Его парсер понимает today/yesterday, русские месяцы и ISO; английские названия месяцев и AM/PM не реализованы (`1033-1056`). Поэтому перенос этого парсера ухудшил бы уже добавленную нами поддержку английского MAX.
- Время внутри media player специально исключается из поиска метаданных сообщения (`1059-1077`): иначе длительность записи может стать временем сообщения. Это стоит включить в наши проверки аудио/видео.
- Для канальных постов Firefox вызывает штатное копирование ссылки, перехватывая `clipboard.writeText` только во время сбора (`main-inject.js:5-23`). Перманентная ссылка служит ключом записи, при её отсутствии есть текстовый/media fallback (`content.js:231-251`, `288-298`). Доступность такой ссылки у приватных сообщений из этого не следует.
- При достижении порога item, по умолчанию 800, записи сохраняются в IndexedDB; продолжение открывается по ссылке самого старого собранного поста (`261-264`, `1104-1112`, `1304-1331`). Это перезапускаемые DOM-сессии, **не пагинация внутреннего пользовательского API MAX**. Исследованные части не дают готового API-решения для личных чатов.
- Chrome signature состоит из времени, направления и первых 80 символов текста (`content.js:200-201`), поэтому не является надёжным уникальным ID для одинаковых сообщений.

## Вложения

- Firefox берёт реальные HTTP(S) URL из `currentSrc`, `src`, последнего варианта `srcset`, пропуская inline-placeholder (`content.js:51-64`). URL дополняются по мере обнаружения (`135-142`). Если фото ещё не загружено, bubble прокручивается в центр и URL проверяется до 25 раз по 100 мс (`145-158`). Просмотрщик при этом не открывается.
- Для `i.oneme.ru` реализация добавляет `fn=external_28`, если `fn` ещё отсутствует (`898-904`). Комментарий автора утверждает, что это оригинал; **здесь формат/качество ответа не проверены**. Использовать как гипотезу для сравнения Content-Type, размера, размеров изображения и реального ответа, не как гарантию оригинального разрешения.
- Распознаются `.attachAudio`, `.attachVideo`, `.sticker`, `.videoMessage`, общие документы (`420-449`). Наличие распознавания типа не означает скачивание соответствующего бинарного файла: круговое видео там определяется по canvas/длительности, без URL (`467-476`).

## Рекомендуемый порядок проверки в нашем расширении

1. Записать все подходящие scrollpane, выбранный узел, верхнюю границу первого сообщения и его положение относительно viewport. Сравнить с `.history .scrollable`.
2. Воспроизвести из неоткрытого чата, разделить ожидание загрузки чата, подготовку нижнего края и загрузку старых сообщений. Сравнивать первое/последнее сообщение, DOM и состояния загрузчика, а не только `scrollTop`.
3. При отсутствии новых сообщений явно отражать неизвестную полноту. Проверить восстановление на свежей странице без дат и без вложений, затем отдельно с медиа.
4. Для больших каналов исследовать сохраняемые сессии и стабильные ссылки; для личных чатов сначала доказать наличие стабильного ID/ссылки. Не переносить канальный механизм как универсальный.
5. До заявления об исправлении повторить живой экспорт выбранного закрытого чата с известным числом сообщений; синтетическая фикстура и исходники конкурентов этого не заменяют.
